# 创作执行

根据已确认的 `创作规划.yaml` 执行条目创作、质量检查、注册和错误恢复。

## 前置必读

开始创作前，必须先加载：

- `references/rules.md` — 正面写作规则（角色写作要点、世界观压缩）
- `references/rules-check.md` — 写作质量检查清单（创作前自检 + 子代理事后扫描两用）
- `references/conventions.md` — 条目注册约定（命名、文件格式、patch 命令）

**注意**：主代理可读 `references/rules-check.md` 做创作前自检，但**不得把违规范例措辞当作创作素材**，也不得为了规避清单而矫枉过正。

## entries 执行原则

- `创作规划.yaml` 的 `entries` 数组是项目级事实来源，按数组顺序执行。
- 必要时可因依赖关系调整执行顺序，但不得漏条目。
- 若调整会改变用户已确认的条目顺序或内容范围，先同步更新 `创作规划.yaml` 并询问用户确认。

### 编写顺序校验

**世界建构**：

1. 世界观概览先行——其他条目可能引用它，先确立整体框架
2. 区域条目按信息量决定是否拆分，逐区域展开
3. 历史事件最后写——依赖世界观和区域的设定

**角色**（对每个核心角色）：

1. 基础信息 — 必写
2. 性格调色盘 — 必写
3. 三面性 — 可选，仅当角色在不同场景下行为模式有根本性切换时（判断标准见 `references/requirements.md`）
4. 二次解释 — 必写

5 个以上角色时，先编写角色速览（`references/contents-creation/character/character-catalog.md`）。

**角色阶段原则**：

- 每个阶段的行为/变化倾向不是上一阶段的延续，而是该阶段独有的新模式
- 性格底色不会随阶段变化
- 衍生分为**通用衍生**（跨阶段始终存在）和**阶段专属衍生**（仅在该阶段出现）：专属衍生是该阶段才解锁的新行为，不是上一阶段衍生的升级版。同一行为在不同阶段的细微差异通过二次解释体现，不需要跨阶段复制衍生
- 其与三面性的差异在于：行为模式的变化不是由于场景的切换，而是随着剧情发展由人物关系的变化导致

## 条目类型与创作规则对应

| 条目类型 | 创作规则文档 |
|---------|------------|
| 世界观 | `references/contents-creation/worldbuilding/worldview.md` |
| 时间线 | `references/contents-creation/worldbuilding/timeline.md` |
| 地理 | `references/contents-creation/worldbuilding/geography.md` |
| 角色 | `references/contents-creation/character/basic-info.md` 等（见 character/ 目录） |
| NPC | `references/contents-creation/character/npc.md` |
| 事件 | 按 `references/rules.md` 编写，无专门文档 |
| 阶段指导 | `references/contents-creation/stage-guidance.md` |
| 扮演准则 | `references/contents-creation/presentation.md` |

### 时间线 条目

`时间线` 类型通过 `part` 区分：history（历史事件）、plot（当前剧情，仅从材料转化时编写）。

详见 `references/contents-creation/worldbuilding/timeline.md`。

### 阶段指导 条目

阶段化玩法/剧情主持策略条目，必须使用 EJS 条件渲染，通常集中到一条总指导条目。

详见 `references/contents-creation/stage-guidance.md`。

### 扮演准则 条目

呈现方式条目，世界书级别的整体条目（不是角色专属）。

**何时使用**：用户在以下情况需要呈现方式条目：
- 特定世界观下需要约束写作方式（如克苏鲁不希望血腥）
- 叙述风格需要统一指引（如"全篇比喻，但禁止重复意象"）
- 叙事基调需要明确（如"暗黑压抑，但留给希望"）

**rephrase**：用户有特定偏好时设为 true，如血腥规避等。

详见 `references/contents-creation/presentation.md`。

## 条目创作循环

按 typeLists 的位置顺序（before_char → after_char → depth）分组执行：每个位置内逐条完成编写与注册，位置内条目全部注册完成后统一禁词扫描，通过后再进入下一个位置。位置内条目按 `entries` 数组顺序处理。

对当前位置下的每个条目：

0. **规划完整度检查**：位置内首条创作前扫描 `创作规划.yaml` 中是否有 `# 待细化` 注释。如有，先追问用户补全后再创作。同时读 `requirements`，逐条判断是否约束本条目：`must` / `must_not` 必须执行，`prefer` 在与其他要求冲突时让步；界面、打包这类不落到条目正文的要求跳过。本条目 `note` 里的要求同样执行。原文有歧义、或判断不了这条要求是否已满足时，先问用户，不要自己补判据。
1. **读取创作规则**：根据条目类型加载对应的创作规则文档（见上方对应表）
2. **读取前置 CoT 依据**：加载 `references/rules-check.md`（创作前自检与子代理扫描的共通检查清单）
3. **前置 CoT 自检**（必须，每条）：在内部按 `references/rules-check.md` 预演本次要写的内容，命中违规范例即调整写作思路。详见下文「前置 CoT 自检」节。
4. **编写条目内容**：根据规划信息 + 类型规则编写，**按自检通过的思路写**，遵循 `references/rules.md`
   - 从材料转化而来，且故事大纲或创作规划中存在 `important_chapters[].quotes[]` / `characters[].quotes[]` 原文引用字段时，优先把这些原句作为角色性格、行为边界、关系动态和世界观揭示的依据，避免只用转述概括。
5. **处理 EJS**（如需）：条目在规划文档的 `ejs.entries` 中时，按 `complexity` 一并处理（见 `references/conventions.md`）
6. **写入文件**：将条目内容写入对应文件路径
7. **机械自检**：文件落盘后立即运行 `node scripts/mechanical-check.mjs {file}`（脚本位于本 skill 的 `scripts/` 目录，`{file}` 传条目文件路径），不通过就地修正后再进入步骤 8。脚本检查破折号、模糊词、否定转折、极端程度词、元叙事标记、`{{user}}` 宏，以及断句（短尾比例、单句分句数上限）。EJS 与酒馆宏不参与判定；含连续拉丁字母的行只作提示，人工排除合规术语。有硬违规或断句超阈值时退出码为 1。断句项命中「例外」（台词、紧张场景）时可保留，在自检记录里写明理由。
8. **立即注册**（不可跳过）：立即运行 patch 命令注册到 entryManifest（见 `references/conventions.md`）
   - 注册是断点续接的唯一判断依据，不注册 = 条目被视为未完成
   - 每个条目写完必须立即注册，禁止积攒多个条目后批量注册

继续位置内下一个条目。位置内全部条目注册完成后：

9. **位置级禁词扫描**（必须）：使用**独立检查上下文**，将该位置所有条目一起送检 `check-agent`。有问题则按下方说明修正后重扫，直到通过。

通过后进入下一个位置。

**约束**：步骤 3、步骤 7、步骤 9 不可跳过。步骤 3 是每条创作前的前置自检，步骤 7 是落盘后的单文件机械自检，步骤 9 是每个位置完成后的子代理扫描兜底。注册是断点续接的判断依据，每条写完立即注册（步骤 8）；质量关卡由前置自检（每条）、机械自检（每条）与位置级扫描（每个位置）共同承担。

注意：常见动作词不算八股，不要矫正过度。详见 `references/rules-check.md` 的例外说明。

### 独立检查上下文（禁词扫描）

独立检查上下文的调用方式：调用 `check-agent`，一次送检当前位置的全部条目，既能查单条内部问题，也能查同位置条目间的重复或标签化。送检时向 task 字符串传入需检查条目的**文件路径**，并附内容类型与所属角色/世界观提示。

**检查内容**（按 `references/rules-check.md`）：
- 绝对零度 → 删除或改写
- 八股化 → 删除或改写
- 断句 → 合并短句或补成完整分句
- 具体性 → 改写
- 假性主体与远距离叙事 → 改写
- 翻译腔 → 改写
- 元叙事 → 删除
- 跨条目重复 → 相关条目一起改
- 跨条目引用 → 补全或删除

检查不通过时，先改完扫描报告列出的全部问题，然后检查改写不产生同类新问题，才重扫。
abstract、keywords、路径等注册字段若有变化，禁词扫描通过后再按 `references/conventions.md` 更新。

### 三道防线协作

条目创作的质量由三道防线保障（均为不可跳过的强制步骤），共用 `references/rules-check.md` 这份清单：

|        | 第一道防线（前置 CoT 自检） | 第二道防线（机械自检） | 第三道防线（位置级禁词扫描） |
|--------|---------------------------|----------------------|---------------------------|
| 时机   | 每条创作前（步骤 3）  | 单条落盘后（步骤 7）   | 位置完成后（步骤 9）       |
| 执行   | 主代理内部推理       | 主代理运行 mechanical-check.mjs | 子代理独立上下文           |
| 侧重   | 按单条预演要写的内容  | 单文件硬检查，拦截已知机械模式 | 跨条目重复与语义判罚      |
| 不通过  | —                 | 就地修正，不注册      | 改完全部问题并自查无同类新问题后再重扫 |

三道防线依次加码：第一道防**落笔前**，第二道防**落盘后、注册前**，第三道防**位置收官**。越往后成本越高，越靠前解决问题越省 token。

### 前置 CoT 自检

创作前主代理在内部按 `references/rules-check.md` 预演本次要写的内容，命中任一违规范例即调整写作思路，避免落到文字再返工。

**力度分档**：

| 场景 | 自检范围 |
|------|---------|
| 自动生成 | 完整自检：逐项过 `rules-check.md` 全部小节 |
| 手写指导 | 仅对 AI 补全/生成的部分自检，用户写的内容不查 |
| 修改已有条目 | 增量自检：只查修改/新增部分 |

**修正前自检**：被 `check-agent` 扫描报告命中后、修订已落文字前先做一次轻量预演自检，详见 `references/revision.md#用户反馈不满意`。

## 条目完成 DoubleCheck

所有条目编写完成后、进入技术层之前，执行以下检查。完整性、全局一致性、格式规范为必须项，不通过则修正后重新检查；全局禁词扫描是否执行，询问用户后决定。

### 完整性

- 规划文档中 `entries` 数组列出的条目是否都已编写
- 所有已编写的条目是否都已注册到 entryManifest（文件存在但未注册 = 未完成）
- 跳过的条目是否已记录原因

### 全局一致性

- 同一角色在不同条目中的描述是否矛盾（外貌、性格、关系）
- 世界观条目之间是否存在设定冲突
- 角色关系描述是否双向一致（A 条目说"与B是敌人"，B 条目也要对应）

### 全局禁词扫描（可选）

位置级扫描（步骤 9）已覆盖同一位置内的文字问题。全局扫描进一步检查跨位置的条目问题：

- 上下文引入的八股化：单独看没问题，多个条目放一起重复了同一个比喻/句式
- 角色间标签化：A 和 B 都用了"温柔善良"，但两人的"温柔"应该完全不同
- 世界观压缩检查：按 `references/rules.md` 逐句检查

向用户说明该扫描用于检查跨条目的文字重复与标签化，并询问是否执行；用户对当前文字质量满意时可跳过。需要执行时使用独立检查上下文，将所有条目一起送检。

### 格式规范

- YAML 格式正确（缩进、冒号、列表）
- XML 标签闭合正确
- 条目使用数据库格式，不是散文
- 命名和路径符合 `references/conventions.md`
- 所有条目内容无繁体字、日文汉字（检查角色名、地名、变量名等）
- entryManifest 中 keywords 无单汉字（如"樱""萤""玲"→改为"小樱""小萤""小玲"）

## MVU 一致性检查

MVU 和 EJS 编写完成后执行（SKILL.md 主流程第 7 步），详见 `references/mvu/guide.md` 收尾步骤第 4 步。

## 错误恢复

修改类场景处理见 `references/revision.md`；patch 失败等错误处理见 `references/error-handling.md`。

### 常见场景速查

| 场景 | 处理方式 |
|------|----------|
| 信息不足 | 核心信息立即询问补充；补充信息暂记 `# 待补充`，条目编写前统一询问 |
| 用户反馈不满意 | 收齐修改要求 → 更新创作规划.yaml → 修正 → 重跑禁词扫描 → 更新 abstract |
| 需求变更 | 收齐修改要求 → 评估影响 → 更新规划 → 同步修改条目 |
| patch 失败 | 解读错误 → 修正 → 重新执行 |
| 条目间一致性冲突 | 列出冲突 → 询问用户 → 收齐修改要求 → 更新规划 → 统一修改 |
